# 分層測試：Integration、E2E、Postman

## User Story

身為開發者，我希望能從不同層級自動驗證「會員 → 購物車 → 含運費建單 → 綠界付款」的完整流程，以便改動程式時確認沒有破壞既有功能，而且執行測試不會弄髒專案資料庫。

身為 API 使用者，我希望有一份可直接匯入 Postman 的 Collection，登入後自動帶入 token，以便手動測試所有 API。

## Spec

### 背景與現況

- 運費功能已完成並 commit（`feat: 新增配送運費模組並整合建單流程`、`test: 新增 shipping 單元測試與 test:unit 指令`、`docs: 更新運費相關文件與 openapi`）
- `src/database.js` 的 DB 路徑寫死為 `database.sqlite`，`npm test` 會寫入真實 DB；Integration Test 必須**不修改** `database.sqlite`
- 未安裝 `@playwright/test`、`openapi-to-postmanv2`；本機沒有 Playwright 瀏覽器
- 既有 6 支 API 測試各自建立資料、只依賴 seed；vitest 預設 `isolate: true`、`NODE_ENV=test` → 每個測試檔可各用一份記憶體 DB

### 指令

| 指令 | 內容 | 範圍 |
|---|---|---|
| `npm run test:unit` | `vitest run` | `test/**/*.test.js`、`tests/*.test.js` |
| `npm run test:integration` | `vitest run --config vitest.integration.config.js` | `tests/integration/**/*.test.js` |
| `npm run test:e2e` | `playwright test` | `e2e/`，使用已啟動的 `http://localhost:3001` |
| `npm run postman` | `npm run openapi && node scripts/generate-postman.js` | 輸出 `postman/` |
| `npm test` | `npm run test:unit && npm run test:integration` | — |

`vitest.config.js` 的 `tests/*.test.js` 不遞迴，因此 unit 與 integration 不重複執行。

### 已確認決策

| 議題 | 決定 | 理由 |
|---|---|---|
| 哪些測試用記憶體 DB | **全部** vitest 測試 | 同時解決 `test:unit` 寫入真實 DB 的問題 |
| E2E 瀏覽器來源 | 雙模式 | 有 `E2E_CDP_URL` 時 attach 已開啟的 Chrome；未設定時由 Playwright 啟動 Chromium，clone 專案後可直接執行 |
| Postman 產物 | 輸出 `postman/` 並 gitignore | 可隨時由 `npm run postman` 重新產生，不 commit 產物 |

### 環境變數

| 變數 | 用途 | 預設值 |
|---|---|---|
| `DB_PATH` | SQLite 檔案路徑 | 專案根目錄 `database.sqlite`；vitest 設定為 `:memory:` |
| `E2E_CDP_URL` | E2E attach 既有 Chrome 的 CDP 位址 | 無（改由 Playwright 啟動 Chromium） |
| `E2E_BASE_URL` | E2E 目標網址 | `http://localhost:3001` |

`dotenv` 不覆寫已存在的環境變數，因此 vitest `env` 設定的 `DB_PATH` 優先於 `.env`。

### Integration Test（`tests/integration/order-flow.test.js`）

- 沿用 `tests/setup.js` 的 `app`、`request`、`registerUser`
- `require('../../src/database')` 取得與 app 同一個記憶體 DB 連線，直接查表驗證
- `beforeAll`：以 API 註冊測試會員、`GET /api/products?limit=100` 取一個價格 < 1,500 且庫存 ≥ 10 的商品，並記錄所有商品原始庫存
- `beforeEach`：清空該會員購物車
- `afterAll`：刪除本檔建立的 `order_items`、`orders`、`cart_items`、`users`，還原所有商品庫存

| # | 情境 | 操作 | 驗證 |
|---|---|---|---|
| 1 | 宅配、小計 < 1,500 | 加入 1 件 → 建單（宅配） | 201、`{ data, error: null, message }`；回應與 `orders` 列：配送方式、旗標、`subtotal_amount`、`shipping_fee = 120`、`total_amount`、`pending`、收件資訊；`order_items` 1 筆且價格快照與數量正確；庫存 = 建單前 − 1；`GET /api/cart` 與 DB 購物車皆為空 |
| 2 | 滿額免運 + 附加費 | 加入 `ceil(1500 / 價格)` 件 → 建單（宅配 + 偏遠 + 急件） | 小計 ≥ 1,500；`shipping_fee = 450`；DB 旗標為 1；品項數量；庫存扣除；購物車清空 |
| 3 | 庫存不足 | 加入 2 件後以 DB 將庫存改為 1 → 建單 | 400 `STOCK_INSUFFICIENT`；會員訂單數不變；無孤兒 `order_items`；庫存仍為 1；購物車保留 2 件 |
| 4 | 交易中途失敗 | 建立 `TEMP TRIGGER` 讓 `order_items` INSERT 時 `RAISE(ABORT)` → 建單（超商） | 500、`data: null`；會員訂單數不變（證明已 INSERT 的 `orders` 被 rollback）；無孤兒品項；庫存不變；購物車保留；`finally` 移除 trigger 並還原 `console.error` |
| 5 | 配送方式不合法 | `shippingMethod: 'drone'` | 400 `VALIDATION_ERROR`；訂單數、庫存不變；購物車保留 |

### E2E Test

**設定**
- `playwright.config.js`：`testDir: 'e2e'`、`timeout: 180s`、`expect.timeout: 20s`、`workers: 1`、`baseURL`、失敗時截圖、`trace: retain-on-failure`、`list` + `html` reporter，無 `webServer`
- `e2e/fixtures.js`：覆寫 worker 層級 `browser` fixture
  - 有 `E2E_CDP_URL` → `playwright.chromium.connectOverCDP()`，Playwright 預設 `context` fixture 會建立新 context，不影響既有分頁與登入狀態；結束時 `browser.close()` 只關閉測試建立的 context 並斷線
  - 否則 → `playwright.chromium.launch(launchOptions)`

**流程（`e2e/checkout-payment.spec.js`，共 15 步）**

| 步驟 | 做法 |
|---|---|
| 1. 登入 | `/login` 填 `ADMIN_EMAIL` / `ADMIN_PASSWORD`（預設 `admin@hexschool.com` / `12345678`），等待導回 `/`；以 `Auth.getAuthHeaders()` 取得 token |
| 2. 加入購物車 | 先以 API 清空該帳號購物車；首頁點第一個「加入購物車」，等待 `POST /api/cart` 成功 |
| 3. 進入結帳 | `/cart` → 「前往結帳」→ `/checkout` |
| 4. 填寫資料 | 以 placeholder 填收件人、Email、地址；勾選 `shippingMethod=home_delivery`，等待 `shipping-quote` 回應並確認畫面總計 |
| 5. 建立訂單 | 點「確認送出訂單」確認 `POST /api/orders` 為 201；從網址取訂單 id，以 API 確認 `pending`、配送方式、總額與試算一致 |
| 6. 前往綠界 | 點「前往綠界付款」，等待 `payment-stage.ecpay.com.tw` |
| 7–11. 付款 | 網路 ATM → 選台灣土地銀行 → 前往付款 → 關閉提示視窗 → 土地銀行模擬頁 `Save` |
| 12–13. 返回商店 | 接受兩種情況：出現「返回商店」就點擊；或綠界自動導回訂單頁。實際路徑寫入 annotation `ecpay-return` |
| 14. 已付款 | 頁面出現「已付款」 |
| 15. 狀態 paid | 以 API `GET /api/orders/:id` 驗證 `status === 'paid'`（主判準） |
| 截圖 | 全頁截圖存 `e2e/screenshots/paid-<訂單編號>.png` 並附加到報告 |

綠界頁面選擇器集中於 spec 開頭的 `ECPAY` 常數。E2E 會在 `database.sqlite` 真實新增訂單並扣庫存。

### Postman（`scripts/generate-postman.js`）

- 讀 `openapi.json`，以 `openapi-to-postmanv2` 轉換（`folderStrategy: 'Tags'`、`requestParametersResolution: 'Example'`）
- 後處理：
  - 所有請求 URL 改為 `{{baseUrl}}/...`
  - Collection 變數：`baseUrl = http://localhost:3001`、`token = ''`、`sessionId = ''`
  - Collection 層 `auth: bearer {{token}}`；依 OpenAPI 的 `security` 判斷，需登入的端點繼承，公開端點設 `noauth`
  - 非必填 query 參數預設停用（`page`、`limit` 除外）
  - 購物車端點加上停用中的 `X-Session-Id: {{sessionId}}` header
  - `POST /api/auth/login`、`POST /api/auth/register` 加 test script：2xx 且有 `data.token` 時 `pm.collectionVariables.set('token', ...)`
  - 移除轉換器產生的空 `event`
- 輸出 `postman/flower-shop.postman_collection.json`，寫入後重新 `JSON.parse` 驗證，失敗 exit 1

### 實作與原計畫差異

| 原計畫 | 實際 | 原因 |
|---|---|---|
| `e2e/fixtures.js` 覆寫 `page` fixture | 覆寫 worker 層級 `browser` fixture | 覆寫 `page` 時預設 `browser` 仍會先啟動 Chromium |
| 攔截 `POST /api/orders` 回應取得訂單資料 | 從網址取 id，再以 API 查詢 | 建單後頁面立即跳轉，回應 body 已無法讀取（`Network.getResponseBody` 失敗） |
| 等待「返回商店」再點擊 | 接受「返回商店」或自動導回兩種路徑 | 專案 `src/utils/ecpay.js`（commit `9c3980e`）設定 `OrderResultURL` 且未設定 `ClientBackURL`；依[綠界文件](https://developers.ecpay.com.tw/?p=2862)，付款完成後會直接導回、不顯示「返回商店」。曾誤判為綠界 staging 行為，查證後更正；決定不修改既有付款設定，付款後以自動導回返回站點，並於文件說明 |
| Postman 保留轉換器預設 query 與 event | 停用非必填 query、移除空 event | 範例值 `status=failed` 會意外過濾後台訂單列表 |
